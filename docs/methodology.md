# Methodology

How every `gpubench` experiment is run and measured, independent of what a given experiment is
testing (see `docs/writeup.md` for that). Applies to every experiment under `bench/experiments/`.

## Load generator

Load is generated by vLLM's own benchmarking CLI, never a third-party tool. Engine experiments
(`kind: engine`) use `vllm bench sweep serve`, which starts the vLLM server itself and drives
`vllm bench serve` against it from the same container image in the same pod, over loopback —
client and server always share the exact vLLM build under test. Platform experiments
(`kind: platform`) target an already-running server reached at its in-cluster Service URL, rather
than one the harness starts itself; the client still runs `vllm bench serve` from the harness's
own image (`vllm/vllm-openai:v0.28.0` by default) against that target's OpenAI-compatible
endpoint. Experiment `07-kserve-vs-raw` pins its raw-Deployment target to vLLM `v0.24.0` to match
KServe's bundled runtime, so that mismatch is deliberate rather than accidental engine drift.

## Dataset

The default dataset is ShareGPT (`ShareGPT_V3_unfiltered_cleaned_split.json`), fetched at Job
start by a `curl` init container into `/data/sharegpt.json`. When an experiment pins a `sha256`,
the init container verifies it with `sha256sum -c` before the benchmark container starts, so a
changed or corrupted download fails the Job loudly instead of silently shifting the input
distribution. The smoke test uses the harness's synthetic `random` dataset instead, where length
matters more than realism.

## Runs and statistics

Every load point uses `--seed 0` for a reproducible request schedule and runs three times
(`num_runs: 3`, the harness default), via `vllm bench sweep serve --num-runs` for engine
experiments or a repeated invocation for platform ones. `gpubench report` groups results by
(label, GPU, concurrency) and reports the mean of the three runs' throughput and latency figures.
All three raw `--save-result` JSON files per point are committed under `results/<run>/raw/`, not
just the mean, so the summary can be recomputed independently.

## Metrics and SLOs

Each run requests `--percentile-metrics ttft,tpot,itl,e2el` at `--metric-percentiles 50,90,99`:
time-to-first-token, time-per-output-token, inter-token latency and end-to-end latency are all
reported at p50/p90/p99, not mean alone. A goodput SLO of `--goodput ttft:500 tpot:50` (500ms
TTFT, 50ms TPOT) is attached to every run, so `request_goodput` — the fraction of requests inside
both bounds — sits next to raw throughput in every summary table.

## Errors

`vllm bench serve` reports `completed` and `failed` counts per run; `gpubench` derives an error
rate (`failed / (completed + failed)`) and reports its mean per concurrency step in the same
`summary.md` row as that step's throughput and cost — a concurrency level that only "works" by
shedding requests stays visible, not hidden behind a healthy-looking throughput number.

## Network path

Nothing in the measurement path crosses a `kubectl port-forward`. Engine experiments run the
vLLM server and its benchmark client in the same pod over `127.0.0.1:8000`; platform experiments
hit the target's in-cluster `ClusterIP` Service DNS name directly (e.g.
`http://vllm-single.bench.svc:8000`) from a client pod on the `system` node pool. Both paths stay
inside the cluster network end to end, so latency numbers reflect the serving path itself.

## Server defaults

Every variant sets `--gpu-memory-utilization 0.92`. Prefix caching and chunked prefill are both
on by default in vLLM `v0.28.0` and stay on unless an experiment is testing them directly
(`05-prefix-cache-control` is the one exception). No experiment other than `04-batching` overrides
`max-num-batched-tokens` or `max-num-seqs`, so every other run uses vLLM's own serving defaults on
both L4 and A100-40GB: `max_num_batched_tokens=2048`, `max_num_seqs=256`.

## Provenance

`gpubench collect` writes one `manifest.json` per results directory: `collected_at` (UTC
timestamp), `git_sha` (the harness commit that produced the run), `experiment` (the full
validated experiment definition), `image_ids` (resolved image digests per Job pod, not tags),
`gpu_driver_versions` (read from node labels), and `price` (the exact `bench/prices.yaml` row used
for that run's cost numbers) — enough to audit or reproduce a result without replaying git
history.
